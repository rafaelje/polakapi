Historial de prompts en SQLite

Propuesta de feature · captura nativa vía hooks/plugins de cada CLI LLM para sesiones abiertas desde el panel de terminales (sin captura de keystrokes)

estado: propuesta motor: rusqlite (bundled) alcance: módulo terminal rótulo: sin keylogger

1 · Problema

El panel de terminales puede lanzar directamente un CLI LLM (claude, codex, opencode) como sesión PTY — ver ALLOWED_AI_CLI_BASENAMES en src-tauri/src/pty.rs:24 y la validación en pty.rs:218. Hoy, lo que el usuario envía y lo que el agente responde solo existe como stream en vivo emitido por el reader thread (pty.rs:142) al evento pty:data. Al cerrar la pestaña, se pierde. No hay historial consultable, ni búsqueda, ni forma de revisar qué se preguntó y respondió.

2 · Principio rector: sin captura de keystrokes

La captura de keystrokes del PTY no es una opción: aunque sea local y benévola, los AVs la detectan como keylogger, rompe la confianza del usuario y reconstruir el prompt desde raw keystrokes (backspaces, flechas, Ctrl+U, pegados multi-línea) es inherentemente con pérdidas.

En su lugar, los propios CLIs nos entregan el prompt ya hecho y la respuesta ya generada a través de sus mecanismos de extensión nativos (hooks / plugins). polakapi registra un integrador por CLI y deja que el CLI mismo lo invoque. Esto no toca el stream PTY, no intercepta entrada del usuario, y no añade superficie de seguridad beyond el mecanismo de sandboxing que ya aplica cada CLI a sus hooks.

El PTY sigue siendo el mero transporte de render (xterm.js + pty:data + pty:exit). La captura ocurre fuera del PTY, en el proceso del CLI o en un subproceso que el CLI lanza.

3 · Alcance y definiciones

  • Sesión = una pestaña del panel de terminales cuyo comando spawnado es un CLI LLM. Se identifica por el pty_id que pty_spawn devuelve (pty.rs:130). 1 sesión por pestaña.
  • Prompt = cada envío del usuario al CLI + el turno de respuesta del agente asociado. Capturado como texto estructurado entregado por el hook/evento del CLI, no como keystrokes.
  • Fuera de alcance:
    • Las invocaciones one-shot de /loop (run_loop_agent en loop_cli.rs:90) — ya tienen su propio árbol de archivos y logs.
    • PTYs de shell puro (bash, zsh, …).
    • CLIs LLM ejecutados como one-shot dentro de un shell PTY (p.ej. escribir claude -p "..." en bash) — la sesión es de shell, no de AI CLI directo, y por la regla "sin keystrokes" no podemos parsear el stream.
    • Captura en tiempo real cuando el CLI no la soporta (ver opencode más abajo).

4 · Arquitectura

Azul: flujo PTY existente (apertura de pestaña y render), sin cambios. Verde: la captura nativa — cada CLI LLM invoca a su hook/plugin registrado, que escribe al helper polakapi-capture o al SDK的过程 de opencode, sin tocar el stream PTY. Morado: la ruta de solo lectura para la futura UI de historial.

5 · El puente polakapi ↔ CLI

Cada CLI LLM se ejecuta como hijo del PTY y hereda su entorno. polakapi inyecta, en pty_spawn (commands.rs:14), variables de entorno cuando el command cae en ALLOWED_AI_CLI_BASENAMES:

  • POLAKAPI_PTY_ID = el id de la sesión PTY (pestaña).
  • POLAKAPI_DB_PATH = ruta absoluta a polakapi.db.
  • POLAKAPI_HELPER = ruta al binario polakapi-capture.

El hook/plugin lee estas variables del entorno (los hooks de Claude/Codex heredan el env del CLI; el plugin de opencode corre en-proceso y también ve process.env) y las usa para asociar el prompt a la pestaña correcta y para saber dónde escribir. La captura es best-effort: si el insert falla, se loggea y se continúa — nunca se bloquea la invocación del CLI ni se interrumpe al usuario.

6 · Diseño por CLI

Claude Code · settings.json hook

Evento Field en stdin Uso
SessionStart session_id, source, cwd Crea fila en sessions (mapea session_id de Claude ↔ POLAKAPI_PTY_ID).
UserPromptSubmit prompt (string exacto) Inserta fila prompts con user_input.
Stop last_assistant_message (string) Actualiza la fila prompts del turno con response_text.
SessionEnd reason Cierra la sesión en DB (closed_at).

Fallback si last_assistant_message no ba en Stop: parsear transcript_path (JSONL estble según la doc). Registro: polakapi añade un bloque hooks a ~/.claude/settings.json apuntando a ${POLAKAPI_HELPER} (o a un script wrapper shipped con polakapi).

Codex · hooks.json hook

Igual que Claude — mismos 4 eventos, mismo field prompt (en UserPromptSubmit) y last_assistant_message (en Stop, puede ser null). Registro en ~/.codex/hooks.json o <repo>/.codex/hooks.json.

Caveat Codex (flujo de trust): los hooks non-managed deben revisarse y confiarse vía /hooks antes de correr — Codex guarda el hash y exige re-trust si el script cambia. polakapi puede escribir el hooks.json, pero el usuario debe aceptarlo una vez. Existe --dangerously-bypass-hook-trust para automatización, pero no es el default y no lo activaremos por prefencia.

opencode · plugin .ts

opencode no tiene un evento UserPromptSubmit equivalente: tui.prompt.append es manipulación del TUI, no envío. La captura es post-turno: el plugin escucha session.idle (fin de turno del agente) y llama al SDK client.session.messages({ path: { id } }), que devuelve [{ info, parts: [] }]. Itera parts para armar user_input (filtrando por info.role === "user") y response_text (info.role === "assistant").

Caveat opencode (no real-time): la captura ocurre al final del turno, no por cada envío. Para el historial es suficiente, pero el UX de la UI de historial debe entender que el prompt puede no estar visible hasta que el agente termina de responder. Si el usuario aborta el turno (Ctrl+C), el evento session.idle puede no dispararse con todos los mensajes — hay que manejarlo como best-effort.

Registro: ~/.config/opencode/plugins/polakapi-capture.ts (cargado automáticamente por opencode desde el directorio global de plugins) o como paquete npm añadido a opencode.json → plugin. El plugin tiene acceso al SDK client en-proceso, así que no necesita el helper CLI externo — escribe directo a polakapi.db vía bun:sqlite (que ya está disponible porque opencode corre sobre Bun).

7 · Decisiones de diseño

Motor: rusqlite bundled, no tauri-plugin-sql

El repo ya sigue el principio de que Rust es dueño del estado pesado (PTYs en PtyStore, árbol de archivos de runs). Con rusqlite la escritura ocurre vía el helper polakapi-capture (subproceso lanzado por los hooks de Claude/Codex) o vía el SDK del plugin de opencode, sin exponer SQL al frontend y sin ampliar las capabilities de Tauri. Los comandos de lectura son los únicos expuestos al frontend, tipados.

Esquema (2 tablas, una por sesión-pestaña)

Tabla Columnas Notas
sessions id, pty_id, cli, cli_session_id, cwd, title, status, created_at, closed_at 1 fila por pestaña del panel de terminales cuyo comando spawnado es un AI CLI. pty_id viene de POLAKAPI_PTY_ID; cli_session_id es el session_id que entrega el CLI en sus hooks (distinto para Claude vs Codex vs opencode). title = primer prompt truncado.
prompts id, session_id (FK a sessions.id), seq, user_input, response_text, tokens_in, tokens_out, cost_usd, elapsed_ms, error, created_at 1 fila por turno (prompt + respuesta). Índices en session_id y created_at. tokens_in/out y cost_usd son nullable: los CLIs no los entregan en modo interactivo/stream en sus hooks.
  • No se guarda system_prompt ni snapshot de archivos: en sesiones del panel de terminales no hay "system prompt editable por run" como en /loop — el contexto se acumula en la sesión del propio CLI. Guardar solo el turno user/assistant es lo que tiene valor.
  • Modo WAL obligatorio: varias pestañas PTY pueden estar activas a la vez y varios hooks pueden correr concurrentemente.

Helper polakapi-capture

Binario Rust pequeño (mismo crate que el backend de Tauri, feature gate aparte o sub-comando) que lee JSON de stdin, lo valida contra un schema mínimo y lo inserta en polakapi.db vía rusqlite. Lo llaman los hooks de Claude y Codex. El plugin de opencode no lo necesita (escribe directo vía Bun). Env vars que usa: POLAKAPI_DB_PATH (requerida) y POLAKAPI_PTY_ID (para lookup de sesión).

Estado de Tauri y concurrencia

Db se guarda como State<Mutex<Db>> en tauri::Builder, igual que PtyStore hoy. Esto cubre los comandos de lectura del frontend. Las escrituras desde los hooks vienen del helper polakapi-capture (proceso aparte que abre su propia conexión a polakapi.db en modo WAL) — no compiten por el mutex del backend de Tauri. El plugin de opencode también abre su conexión propia (vía Bun). WAL cubre la concurrencia entre writers.

Migraciones

Tabla schema_version + scripts SQL embebidos con include_str!("migrations/0001_init.sql"). Sin librería externa — mantiene el árbol de dependencias minimalista, alineado con el principio del README de capabilities mínimas. Las migraciones se aplican al arrancar la app (desde el backend de Tauri) y también, de forma idempotente, desde el helper polakapi-capture al arranque (por si se invoca antes de que Tauri arranque).

8 · Fases de implementación

Fase Contenido Entregable
1 · Infra Módulo db.rs: apertura, migración versionada, tests (estilo pty.rs). Helper polakapi-capture como sub-comando del mismo binario. Registrar State<Mutex<Db>> en tauri::Builder. Base creada y migrada al arrancar la app.
2 · Inyección de env Instrumentar pty_spawn para que, si el command es un AI CLI, añada POLAKAPI_PTY_ID, POLAKAPI_DB_PATH, POLAKAPI_HELPER al env del hijo. Sesiones AI CLI marcadas y bridge env activo.
3 · Integrador Claude Script wrapper polakapi-hook-claude.{sh,ps1} shipped con la app; registro en ~/.claude/settings.json (idempotente, no sobrescribe hooks del usuario). Hooks SessionStart, UserPromptSubmit, Stop, SessionEnd hacia polakapi-capture. Historial poblado en sessions PTY de Claude.
4 · Integrador Codex Mismo patrón que Claude; registro en ~/.codex/hooks.json. Documentar el flujo de /hooks trust requerido. Historial poblado en sessions PTY de Codex.
5 · Integrador opencode Plugin ~/.config/opencode/plugins/polakapi-capture.ts: escucha session.idle, llama client.session.messages(...), filtra user/assistant por info.role, escribe a polakapi.db vía bun:sqlite. Historial poblado en sessions PTY de opencode (post-turno).
6 · Consulta + UI Comandos de lectura (list_sessions, list_by_session, search) + vista de historial. list_by_session excluye response_text / user_input del listado; se devuelven solo bajo demanda por id. Historial navegable desde la app.
7 · Opcional FTS5 para búsqueda, export a Markdown/JSON, retención/purga, extracción de tokens/costo si algún CLI empieza a reportarlos en sus hooks. Según necesidad real de uso.

9 · Riesgos y decisiones abiertas

  • Trust flow en Codex: el usuario debe aceptar el hook una vez vía /hooks. Considerar UX (toast la primera vez que polakapi detecta una sesión de Codex sin hook trusted).
  • opencode no es real-time: la captura es post-turno. Si el usuario aborta, parte del turno puede no llegar a DB. Aceptable para historial; no para telemetría en vivo.
  • opencode plugin via Bun: el plugin es JS/TS. Hay que empaquetarlo (p.ej. como npm propio @polakapi/opencode-plugin) o copiarlo a ~/.config/opencode/plugins/. Considerar versioning del plugin.
  • Idempotencia del registro: polakapi no debe sobrescribir hooks del usuario. Usar merge estructural (solo añadir el bloque si no existe) y dejar nota en el settings.json de que es gestionado por polakapi.
  • Versiones de los CLIs: los schemas de hooks pueden cambiar entre versiones de Claude/Codex/opencode. El helper debe validar el JSON de entrada y fallar soft si falta un field (no romper).
  • Multi-instancia: si polakapi está corriendo en varios proyectos a la vez, cada uno escribe a su propio polakapi.db (en su app_config_dir project-local). Evita colisión global.
  • Privacidad: la base es local en app_config_dir; los prompts pueden contener código del proyecto del usuario — no debe salir de la máquina. El helper no hace network. El plugin de opencode tampoco.
  • Detcción de AVs: al no capturar keystrokes y al ser invocado por el propio CLI como hook/plugin (no inyectando DLLs ni escuchando teclado global), el riesgo de falso positivo de AV es mínimo.
  • ¿UI desde el inicio? La captura (fases 1–5) es independiente de la UI; el esquema no cambia si la UI llega después.
  • Retención: ¿ilimitada o purga configurable? Punto de partida sugerido: ilimitada (volumen bajo), revisar en fase 7.
